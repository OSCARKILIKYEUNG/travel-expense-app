# 設計思路紀錄（從起點到現況）

> **定位**：用**故事與因果**整理「這個 App 為什麼長成這樣」— 包含你一路發現的問題（例如：**一做分人就要連稅一起想**、**新幣別與匯率一定要能存**）。  
> **不取代**：技術交付表、公式細節、commit 對照仍以 **[PRODUCT_ITERATION_2025-03.md](./PRODUCT_ITERATION_2025-03.md)**（§二～§五、§十～§十二、§三 L20+）為準；本檔是 **PM／未來自己回顧用** 的設計敘事。

## 一、起點：要解決什麼

- **核心**：旅遊時用 AI 掃收據、手動補記帳，多旅程、多人分攤，最後能看圖表、匯出。
- **演進**：從單一大型 HTML，到決定 **Vite + React + 可維護架構**，讓之後上 **PWA／原生殼（Capacitor）**、換後端（`DataService` 抽象）都不必整份重寫。  
- **背景脈絡**：見 [HANDOFF.md](../HANDOFF.md)（遷移原因、技術選型、目錄）。

## 二、多人分帳：從「總額正確」到「每人看見的也要正確」

**早期直覺**：一筆支出有實付金額，似乎就夠了。

**實際需求**：當使用者 **只看我或只看某人** 時，不能只把「品項原價」加總當成這個人該承擔的—必須依 **實付與可分配標價之間的關係** 做比例，儀表板與圖表也要跟卡片一致。

**設計結論**：引入 **`personShare.js` 的實攤邏輯**、區分「整張指派給某人」與「多人分攤、行上標人」等情境（細節見迭代檔 §2.1、§十二）。

## 三、關鍵領悟：一做「分人」，稅與退稅就不能假裝不存在

**你察覺到的點**：要分人物花費時，**稅項／退稅結構**也必須一起考慮，否則：

- 畫面上會像「有退稅卻看不出來」或「分人金額與整單實付對不起來」；
- 日本免稅常見 **標價與實付不一致**（退稅差額、手續費），若只用簡單加總會誤導。

**因此長出的能力（概念層）**：

| 議題 | 思路 | 對應實作方向（詳見迭代檔） |
|------|------|---------------------------|
| 實付 vs 標價 | 分攤要用「可退稅池」與實付，不是只看表面小計 | 比例 **r**、有效退稅推算 |
| 固定費（例：佣金） | 不應跟商品一起乘上同一個「退稅比例」 | **固定費行**、可退稅池 **G−F**、**P−F** |
| 細項已是免稅後單價 | 加總會等於實付，看起來像「沒退稅」 | **收據免稅額僅顯示**，不進入實付／分帳公式 |
| 外稅單據 + 分人 | 消費稅在視覺上也要能按人拆分理解 | 分人時 **消費稅（按比例）** 列 |

這一段的**公式與欄位名**以 **[PRODUCT_ITERATION_2025-03.md §十二](./PRODUCT_ITERATION_2025-03.md#十二現版邏輯速查匯率--稅退稅--分帳)** 與程式為準。

## 四、單據不是同一種：類型與「雙價格」

現實收據印法差很多（外稅、免稅、套裝、即刻免稅等）。若 AI 與程式假設只有「一種單據」，錯誤會進到分帳。

**設計思路**：

- 用 **單據類型（receipt_type）** 與 **[RECEIPT_TYPES.md](./RECEIPT_TYPES.md)** 裡的情境 A～H 對齊共識；
- 需要時區分 **標價／實付價（price_actual）**，分帳用 **實際可攤金額**，避免 ZARA 類雙欄位被算錯。

## 五、卡片：掃描期的「對照」與手動修正後的「定案」（2026-03 起）

**你遇到的張力**：掃描進來時，收據上常有 **標價 vs 實付／稅後** 的對照（含品項 `price` 與 `price_actual`），畫面上用刪除線幫使用者讀懂「店內標價」和「實際計入的金額」；但 **使用者一旦在編輯裡改了價格、稅、折扣或品項金額**，再沿用掃描期的對照 UI，反而像在展示**過期的兩套故事**，容易誤解「到底哪個才是我現在認定的數字」。

**設計結論（概念層）**：

| 議題 | 思路 |
|------|------|
| 何時還顯示「掃描對照」 | 僅在 **尚未**因價格相關編輯而「定案」時；以旗標 **`userEditedPricing`**（僅在變更價格／稅／折扣／品項金額等並儲存後為真）區分兩種閱讀模式。 |
| 定案後卡片讀什麼 | **精簡模式**：品項以使用者輸入的 **`price` 為準**，不再用舊的 `price_actual` 蓋過手改金額；必要時在儲存時清掉已過期的 `price_actual`。 |
| 整單折扣 | 資料層早可存 **`discount`**；若不在卡片呈現，等於「只存不顯」— 與使用者對「一張單有哪些加減項」的心智模型不一致，故卡片需有 **折扣列**。 |
| 消費稅／退稅列 | 編輯後仍要看得見稅務欄位的變化：消費稅不宜綁死「僅外稅單據才出列」而讓內含稅等情境像沒改到；退稅列也不應因進入精簡模式就整條消失。 |
| 視覺與加減方向 | 消費稅用 **`+`**、退稅與折扣用 **`-`** 前綴，與使用者對「加稅／扣減」的直覺一致。 |

**與文件的關係**：資料流與欄位說明見 **[DATA_FLOW.md](./DATA_FLOW.md)**；踩坑與 SAVE 快照見 **[PRODUCT_ITERATION_2025-03.md](./PRODUCT_ITERATION_2025-03.md) §三 L20～L22**、**§十（2026-03-27）**。

## 六、多幣別：為什麼「新幣值也要儲存」

**需求直覺**：出國刷卡、收據上什麼幣都有，回家想用 **自己的記帳幣** 看總覽。

**因此必須釐清兩件事**：

1. **記帳幣（home）**：報表、總額換算的基準；**不是**寫死某國貨幣，而是使用者可選（含「其他」自訂 ISO 三字碼）。
2. **旅程主要外幣（trip）**：掃描時 AI **猜不到幣別** 時的預設、與使用者心理預設的「這趟主要花哪種錢」— 與記帳幣 **語意不同**，但都要能選、能存。

**「新幣值要儲存」指什麼**：

- **匯率表**必須落在 **settings**（持久化）：每一種會用到的外幣，對記帳幣的換算係數要留著，不然重開 App 就失真。
- 後續加上 **即時匯率（Frankfurter）** 時，仍要與 **手動表**、**切換記帳幣時的換算（rebase）** 共存—所以「存的不只是數字，而是一套可更新、可還原的匯率狀態」。
- **旅程幣**也支援 **OTHER + 自訂三字碼** 與可刪除的已存清單，與記帳幣體驗對齊，避免「常用小幣永遠要手打」。

詳細 Phase 與坑：**[PRODUCT_ITERATION_2025-03.md §十一](./PRODUCT_ITERATION_2025-03.md#十一多幣別系統2025-03-26-起--計劃--交付--坑--後續)**。

## 七、信任與可讀：介面語言與協作方式

- **i18n（繁中／英）**：介面可切語言；收據欄位可 **雙語**（店名、品名等），避免只適用單一語境。
- **與助手協作**：**意見 → 先對齊 → 再實作**（見 [PRODUCT_MANAGEMENT.md「與 AI 協作 SOP」](./PRODUCT_MANAGEMENT.md#與-ai-協作-sop)），避免細節一丟就被改壞產品假設。
- **SAVE**：重要節點寫入迭代檔 §十，對話不散失。

## 八、一句話時間軸（給未來自己）

1. 先能記帳、掃收據。  
2. 多人分帳 → 必須處理 **實付比例** 與 **退稅／固定費／免稅顯示**。  
3. 真實小票差異大 → **單據類型 + 雙價格 + 驗證／needsReview**。  
4. 手動修正與卡片一致 → **編輯後精簡顯示**、**整單折扣可見**、稅務列與加減符號可讀（見 **§五**）。  
5. 跨國與報表 → **記帳幣 + 旅程幣 + 匯率持久化 + 即時匯率與防呆**。  
6. 用文件與規則讓 **設計決策可追溯**。
